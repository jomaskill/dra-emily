## Component Responsibilities

| Component | Responsibility | File |
|-----------|----------------|------|
| Application bootstrap | Creates the Laravel application and registers web, console, and health routes | `bootstrap/app.php` |
| Web routes | Maps home, procedure, and sitemap URLs | `routes/web.php` |
| Procedure controller | Looks up a slug in configuration, rejects missing data, and selects the configured Blade view | `app/Http/Controllers/ProcedureController.php` |
| Clinic configuration | Centralizes clinic identity, contact, location, analytics, and verification settings | `config/clinic.php` |
| Procedure catalog | Stores SEO copy, facts, benefits, steps, FAQs, view overrides, and relationships for each slug | `config/procedures.php` |
| Shared page shell | Emits document metadata, analytics, Vite assets, schema slot, navigation, and footer | `resources/views/components/site-layout.blade.php` |
| Home page | Renders the marketing landing page and its FAQ/procedure content | `resources/views/welcome.blade.php` |
| Standard procedure page | Renders most procedure entries from the shared config schema | `resources/views/procedure.blade.php` |
| Full Face page | Renders the specialized Full Face page, including facial thirds and included procedures | `resources/views/procedures/full-face.blade.php` |
| Image component | Selects an existing WebP sibling when available and emits responsive image markup | `resources/views/components/picture.blade.php` |
| SEO/schema partials | Emits JSON-LD for home and procedure pages | `resources/views/partials/schema.blade.php`, `resources/views/partials/procedure-schema.blade.php` |

## Pattern Overview

**Overall:** Laravel route/controller/view architecture with configuration-driven content and server-rendered Blade components.

**Key Characteristics:**
- Routes are deliberately small; the home route points directly to a view while procedure lookup is isolated in `ProcedureController`.
- Content is data-first: `config/procedures.php` and `config/faq.php` are the source for repeated visible and SEO content rather than database records.
- `x-site-layout` provides the page-level shell; Blade slots and includes compose page-specific schema and reusable navigation/footer fragments.
- The frontend is mostly static HTML/CSS generated by Blade; `resources/js/app.js` is currently empty and there are no Livewire components in the application tree.

## Layers

**Bootstrap and framework layer:**
- Purpose: Construct the application and connect Laravel’s web/console entry points.
- Location: `bootstrap/app.php`, `bootstrap/providers.php`, `public/index.php`, `artisan`
- Contains: Application configuration, provider registration, and front controllers.
- Depends on: Laravel framework.
- Used by: HTTP requests and Artisan commands.

**Routing and HTTP layer:**
- Purpose: Translate public URLs into view responses or controller actions.
- Location: `routes/web.php`, `app/Http/Controllers`
- Contains: Named routes, route constraints, controller method `show`.
- Depends on: `config/procedures.php` for the slug allow-list and view selection.
- Used by: Browser requests to `/`, `/procedimentos/{slug}`, and `/sitemap.xml`.

**Configuration/content layer:**
- Purpose: Hold business-facing clinic and treatment content in PHP arrays.
- Location: `config/clinic.php`, `config/procedures.php`, `config/faq.php`
- Contains: Contact/location values sourced from environment, procedure records, FAQ records.
- Depends on: Environment values through Laravel `env()` calls.
- Used by: Routes, controller, Blade pages, schema, sitemap, and footer/navigation fragments.

**Presentation layer:**
- Purpose: Render page markup, navigation, calls to action, structured data, and responsive images.
- Location: `resources/views`
- Contains: Full pages, specialized procedure templates, anonymous components, and partials.
- Depends on: Route data, configuration, `public/` assets, and compiled Vite assets.
- Used by: Laravel response rendering.

**Asset layer:**
- Purpose: Define Tailwind theme/utilities and Vite entry points; serve source images and generated assets.
- Location: `resources/css/app.css`, `resources/js/app.js`, `vite.config.js`, `public/`
- Contains: Tailwind v4 CSS, empty JS entry, source/optimized image files, and `public/build` output.
- Depends on: Vite, Laravel Vite plugin, Tailwind Vite plugin.
- Used by: `x-site-layout` via `@vite` and Blade image component via `asset()`.

**Persistence/framework support layer:**
- Purpose: Provide Laravel’s default auth/cache/queue/session scaffolding and SQLite storage.
- Location: `app/Models/User.php`, `database/migrations`, `database/factories`, `database/seeders`, `database/database.sqlite`
- Contains: Default users, cache, and jobs schema plus user factory/seed hooks.
- Depends on: Laravel Eloquent and configured database connection.
- Used by: Framework services; no clinic-domain request path currently queries these records.

## Data Flow

### Primary Home Request Path

1. `public/index.php` boots the application configured by `bootstrap/app.php`.
2. `routes/web.php:6` matches `/` and returns the `welcome` view directly.
3. `resources/views/welcome.blade.php` derives WhatsApp/contact values from `config/clinic.php`, collects procedures from `config/procedures.php`, and reads `config/faq.php` for the visible FAQ.
4. The page invokes `resources/views/components/site-layout.blade.php`, which adds metadata, analytics, Vite assets, navigation, the supplied schema slot, and footer.
5. `resources/views/partials/schema.blade.php` emits JSON-LD using the same clinic and FAQ configuration used by the page.

### Procedure Request Path

1. `routes/web.php:8-10` matches `/procedimentos/{slug}` only when the slug is one of the keys in `config('procedures')`.
2. `app/Http/Controllers/ProcedureController.php:12-21` reads `config("procedures.{$slug}")`, aborts with 404 if absent, and passes `slug` and `procedure` to the configured view.
3. Most records render `resources/views/procedure.blade.php`; the `full-face` record selects `resources/views/procedures/full-face.blade.php` through its `view` key.
4. The selected page invokes `x-site-layout` and includes `resources/views/partials/procedure-schema.blade.php`; page sections iterate facts, benefits, steps, and FAQ arrays from the procedure record.

### Sitemap Request Path

1. `routes/web.php:12-16` returns `resources/views/sitemap.blade.php` with `application/xml` content type.
2. The view creates the home URL and iterates `config('procedures')` to publish each procedure URL, using `config/clinic.php` for the domain.

**State Management:**
- Request state is passed as Blade variables (`$slug`, `$procedure`, and component props); there is no client-side application state or Livewire state.
- Persistent state is limited to Laravel’s default framework model/schema scaffolding; clinic content is static configuration.

## Key Abstractions

**Configuration-backed procedure record:**
- Purpose: Represent all page content and SEO metadata needed by a treatment page.
- Examples: `config/procedures.php`, `app/Http/Controllers/ProcedureController.php`, `resources/views/procedure.blade.php`
- Pattern: Add a slug-keyed array with the common field schema; set `view` only for a specialized template and use `includes`/specialized fields only when that template expects them.

**Anonymous site layout component:**
- Purpose: Keep document-level SEO, analytics, assets, navigation, and footer consistent across pages.
- Examples: `resources/views/components/site-layout.blade.php`, `resources/views/welcome.blade.php`, `resources/views/procedure.blade.php`
- Pattern: Pass required SEO props and provide page-specific JSON-LD through the `schema` named slot.

**Anonymous picture component:**
- Purpose: Provide a single image API with automatic WebP fallback/selection, dimensions, loading, and fetch priority.
- Examples: `resources/views/components/picture.blade.php`, usages in `resources/views/welcome.blade.php` and `resources/views/procedure.blade.php`
- Pattern: Keep the original asset in `public/`; place a same-basename `.webp` beside it and invoke `<x-picture>` with descriptive `alt` text.

**Schema partials:**
- Purpose: Keep structured-data markup separate from visual sections while sourcing it from the same config records.
- Examples: `resources/views/partials/schema.blade.php`, `resources/views/partials/procedure-schema.blade.php`
- Pattern: Include the matching partial inside the layout’s `schema` slot rather than embedding document-level schema in each page body.

## Entry Points

**HTTP front controller:**
- Location: `public/index.php`
- Triggers: Every web request.
- Responsibilities: Load Composer and dispatch into the Laravel application.

**Application bootstrap:**
- Location: `bootstrap/app.php`
- Triggers: HTTP and Artisan startup.
- Responsibilities: Configure base path, web routes, console routes, health endpoint, middleware, and exception hooks.

**Web route table:**
- Location: `routes/web.php`
- Triggers: Browser requests.
- Responsibilities: Publish named home, procedure, and sitemap endpoints.

**CLI entry point:**
- Location: `artisan`, `routes/console.php`
- Triggers: Artisan commands.
- Responsibilities: Start Laravel CLI and register the sample `inspire` command; image conversion is available through `app/Console/Commands/ConvertImagesToWebp.php`.

## Architectural Constraints

- **Threading:** Standard PHP/Laravel request lifecycle; no custom workers or concurrent application code is present.
- **Global state:** Laravel configuration and facades are global framework services; page content is read through `config()` from PHP arrays.
- **Circular imports:** No application-level module import graph exists beyond PHP class autoloading; no circular chain is detected in `app/` or `resources/views`.
- **Content source:** Procedure and FAQ content must remain compatible with the array shape expected by the Blade templates and schema partials.
- **Asset availability:** `<x-picture>` checks the filesystem under `public/`; missing original assets or WebP siblings affect rendered image output.

## Anti-Patterns

### Bypassing the shared layout

**What happens:** A page can emit its own document shell and duplicate metadata, analytics, navigation, or footer instead of using `x-site-layout`.
**Why it's wrong:** It creates inconsistent SEO and site chrome across the small set of landing pages.
**Do this instead:** Add page content inside `resources/views/components/site-layout.blade.php` through `<x-site-layout>` and use its `schema` slot, following `resources/views/welcome.blade.php`.

### Duplicating procedure content in views

**What happens:** Treatment names, facts, FAQ answers, or SEO text are hard-coded separately in multiple Blade templates.
**Why it's wrong:** The home cards, detail page, sitemap, and structured data can drift.
**Do this instead:** Add or update the slug record in `config/procedures.php` and consume it through `app/Http/Controllers/ProcedureController.php` and the existing templates.

## Error Handling

**Strategy:** Use Laravel’s standard HTTP exception handling and fail closed for unknown procedure slugs.

**Patterns:**
- `app/Http/Controllers/ProcedureController.php:16` calls `abort_if(..., 404)` after configuration lookup.
- `routes/web.php:9` constrains procedure routes to configured keys before controller execution.
- `bootstrap/app.php` leaves middleware and exception configuration at framework defaults.

## Cross-Cutting Concerns

**Logging:** Laravel’s configured logging stack in `config/logging.php`; no application-specific logging calls are present in the page/controller path.
**Validation:** Route regex constraints and null checks validate procedure identity; there are no form submissions or request validation classes.
**Authentication:** The default session/Eloquent auth scaffolding is configured in `config/auth.php` and `app/Models/User.php`, but public site routes do not require authentication.
**SEO:** Shared metadata lives in `resources/views/components/site-layout.blade.php`; JSON-LD, canonical URLs, sitemap, and clinic/procedure copy are composed from `config/clinic.php`, `config/faq.php`, and `config/procedures.php`.
